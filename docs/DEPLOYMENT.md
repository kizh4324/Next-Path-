# Deploying Next_Path

Target: **Vercel** (frontend) + **Render** (API) + **Supabase** (PostgreSQL 16), per
`docs/architecture/deployment-and-infrastructure.md`.

Order matters. The API needs the database before it can migrate, and the frontend needs
the API's URL before it can build. Do it in the order below and nothing has to be redone.

---

## Before you start

You need three accounts (all have free tiers): Supabase, Render, Vercel. Optionally a
Google AI Studio key for Gemini — the app works without one.

---

## 1. Database — Supabase

1. **New project.** Pick the region closest to your users (`ap-south-1`, Mumbai). Save
   the database password Supabase generates; it is shown once.
2. **Settings → Database → Connection string → URI.** Copy the **Transaction pooler**
   string — port **6543**, not 5432.

   > Use the pooler. Render's free tier opens more connections than Supabase's direct
   > port allows, and you will hit `FATAL: too many connections` under any real load.

3. Rewrite the scheme for the async driver:

   ```
   postgresql://...            ->  postgresql+asyncpg://...
   ```

   The app auto-corrects a bare `postgresql://`, but being explicit avoids surprises.

4. Keep the final string for step 2. It is the value of `DATABASE_URL`.

---

## 2. API — Render

**Blueprint** → point at this repo. Render reads [`render.yaml`](../render.yaml) and
provisions the service.

Three variables are marked `sync: false`, meaning Render will ask you for them:

| Variable | Value |
|---|---|
| `DATABASE_URL` | The pooled Supabase string from step 1 |
| `CORS_ORIGINS` | Leave blank for now — filled in at step 4 |
| `GEMINI_API_KEY` | Your key, or blank |

`JWT_SECRET_KEY` is generated by Render. Do not set it by hand and never commit one —
the app **refuses to boot** in production while it still holds the development default.

On deploy, the pre-deploy command runs:

```
alembic upgrade head && python -m data.seed_runner
```

This is the moment the migrations run against a real PostgreSQL for the first time.
**Watch the log.** Seeding is idempotent, so a re-deploy converges rather than
duplicating.

Verify:

```bash
curl https://<your-service>.onrender.com/health
# {"status":"ok","environment":"production","llm_configured":true}

curl https://<your-service>.onrender.com/api/v1/careers | head -c 300
# should list 27 careers — an empty array means seeding did not run
```

> **Free tier sleeps after 15 minutes idle.** The first request afterwards takes
> 30–60 seconds. Fine for a demo; upgrade before real users see it.

---

## 3. Frontend — Vercel

**Import project** → set **Root Directory** to `frontend`. Vercel reads
[`frontend/vercel.json`](../frontend/vercel.json) for the rest.

One environment variable:

| Variable | Value |
|---|---|
| `VITE_API_BASE_URL` | `https://<your-service>.onrender.com/api/v1` |

Note the `/api/v1` suffix and **no trailing slash**.

> Vite inlines `VITE_*` variables at build time. Changing this later requires a
> redeploy — editing it in the dashboard alone does nothing.

---

## 4. Close the CORS loop

Go back to Render and set:

```
CORS_ORIGINS = https://<your-project>.vercel.app
```

Exact origin, no trailing slash, no path. Redeploy the API.

Miss this and the app loads but every request fails preflight — the UI looks broken with
nothing useful in the logs.

---

## 5. Verify end to end

1. Open the Vercel URL, create an account.
2. Complete onboarding — you should get 3–5 options with Fit / Feasibility / Evidence
   labels.
3. Open a career with no market data (e.g. Civil Engineer). It must show the explicit
   *"no verified market evidence"* state, not an empty panel.
4. Select a pathway; confirm the roadmap generates.
5. Filter scholarships by a state that is not Maharashtra — you should get All-India
   results plus the coverage note.

## What is deliberately absent

**No student data is seeded.** Only the catalogue: careers, skills, scholarships, market
snapshots. `dev_bootstrap.py` (which creates demo accounts) refuses to run against
PostgreSQL — it is a local-only tool.

**Nobody staffs the counselor queue.** The crisis interceptor still fires, still shows
Tele-MANAS / KIRAN / 112, and still records the incident — but the message states
plainly that the app cannot contact anyone on the student's behalf. If you later staff
the queue, update `build_crisis_response()` in `app/modules/safety_service.py` and add an
alert on `trigger_reason = 'crisis_safety_flag'`.

**No privacy policy or terms.** The app stores minors' profiles and guardian consent
records. Before real students use it, that needs addressing under DPDP.

**No LICENSE file.** Third-party attribution is handled in [`NOTICE.md`](../NOTICE.md)
and is required regardless; the source licence is still an open choice.

## Troubleshooting

| Symptom | Cause |
|---|---|
| `/api/v1/careers` returns `[]` | Seeding did not run. Check the pre-deploy log; run `python -m data.seed_runner` from the Render shell. |
| Recommendations 503 | Empty catalogue — same cause as above. |
| Every request fails in the browser, works in curl | `CORS_ORIGINS` mismatch. Must be the exact Vercel origin. |
| `FATAL: too many connections` | Using the direct Supabase port. Switch to the pooler (6543). |
| App will not start, complains about the secret | `JWT_SECRET_KEY` is still the development default. |
| Chatbot says it is unavailable | No LLM key set. Expected, and the rest of the app is unaffected. |
| First request takes a minute | Render free tier cold start. |
